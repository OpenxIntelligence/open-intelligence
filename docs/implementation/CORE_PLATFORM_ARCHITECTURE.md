# Core platform architecture

The H1 application has one connected clinical persistence boundary. React calls the versioned FastAPI routes; PostgreSQL holds patient, source, evidence and work records. The separate SQLite application preserves useful reference behavior. Qualified adapters can run independently when isolation or resource requirements justify it. They receive scoped inputs and return versioned outputs through the owning domain.

| Domain | Current source of authority | Integration rule |
|---|---|---|
| Patient, organization and identity | [Registry](../../src/open_intelligence/postgres_registry.py), [case bindings](../../apps/api/src/oi_api/case_bindings.py) and [fixture authentication](../../apps/api/src/oi_api/access.py) | Use one patient identifier and an explicit organization-qualified binding. Resolve identity ambiguity before ingest. A production organization directory and verified patient/workforce identity remain open. |
| Consent, authorization and audit | Access policy and final-action checks in the [patient API](../../apps/api/src/oi_api/patients.py), domain-specific receipts and events | Each disclosure, export, research purpose and write has its own permission. Recheck at the actual disclosure/commit boundary. Real consent and caregiver delegation require separate owners and tests. |
| Encounters and notes | Existing clinical reference plus [H1 EHR candidate #535](https://github.com/OpenxIntelligence/open-intelligence/pull/535), brought together in [#542](https://github.com/OpenxIntelligence/open-intelligence/pull/542) | Reuse patient-scoped encounter transitions and immutable note versions. Keep authoring, professional attestation and downstream execution as separate actions. |
| Clinical sources and documents | [Source versions](../../apps/api/src/oi_api/sources.py), [manual document intake](../../apps/api/src/oi_api/reviewed_documents.py) and [source integrity](../../apps/api/src/oi_api/source_integrity.py) | Store original before derived output; retain hash, source version, locators, correction lineage and independent read grants. Distinguish manual entry, document upload, structured API import, future connector and external report. |
| Episodes, diagnoses, pathology, staging and observations | [World Model projection](../../apps/api/src/oi_api/source_world_model.py) and [laboratory source owner](../../apps/api/src/oi_api/laboratory_fhir_store.py) | Model separate tumor/episode/specimen identities. A source-reported label or reference range cannot establish an adjudicated diagnosis, staging decision or progression. See the [clinical data model](CLINICAL_DATA_MODEL.md). |
| Medications, allergies, procedures and treatment | Proposed coordinated clinical domains; descriptive source findings and reference care records exist | Implement reconciliation, reactions and source status first. Link orders, dispensing, administrations and outcomes by version and actor. Avoid inferring administration from a prescription. |
| Imaging and genomics | [Bounded H1 image custody](../../apps/api/src/oi_api/images.py); [reference biological asset lineage](../BIOLOGICAL_ASSET_PROVENANCE.md) | Images retain canonical source identity. Scientific artifacts need input hashes, rights, reference build, reproducible workflow and dedicated disclosure policy. |
| Investigations, evidence and reports | [Source questions](../../apps/api/src/oi_api/source_questions.py), [authored evidence](../../apps/api/src/oi_api/authored_evidence.py), [reports](../../apps/api/src/oi_api/evidence_report.py) | Source and evidence versions are immutable inputs. A hypothesis, comparison, human decision and report each preserve actor, timing and accurate review state. |
| Tasks, workflows and events | [Follow-through tasks](../../apps/api/src/oi_api/question_followthrough.py), owner-specific domain events and command receipts | Record a command, its outcome and event atomically where required. Reuse existing idempotency semantics. The integrated [Composer worker](../../apps/api/src/oi_api/worker.py) and [source-event worker](../../apps/api/src/oi_api/event_worker.py) use the existing PostgreSQL run and outbox owners. A future queue would need a measured requirement. |
| Research, AI and discovery | [AI contracts](AI_PLATFORM_ARCHITECTURE.md), [scientific run contract](BIOINFORMATICS_ARCHITECTURE.md) and [discovery](THERAPEUTIC_DISCOVERY_ARCHITECTURE.md) | Research and hypothesis generation have bounded inputs and explicit purposes. Workers receive no general chart-write authority. Clinical promotion has an independent owner. |

## API and shared infrastructure

The [composition root](../../apps/api/src/oi_api/app.py) provides OpenAPI at `/v1/openapi.json`, readiness and liveness. [Database readiness](../../apps/api/src/oi_api/database.py) checks PostgreSQL major and the exact migration head. Validation errors omit rejected values. Domain owners define input types, plausible bounds, query filters, receipt/retry semantics and errors. Pagination and filtering are endpoint-specific. Introduce a cursor on a large collection only with stable ordering, scope binding and tests for concurrent writes and revocation.

[#543](https://github.com/OpenxIntelligence/open-intelligence/pull/543) makes patient command envelopes safe by default and adds a process-local token budget before parsing. This protects a local H1 process without a broker or an identity-indexed store. Other shared infrastructure still needs acceptance: production authentication/consent, institution-scale quotas, operational observability, durable object storage for large artifacts, scalable workflow recovery and authoritative clinical sign-off.

For source intake, each channel must resolve identity, purpose and source owner before writing. Retain incoming bytes or original authored text, a scoped idempotency receipt, the version and any parser output as distinct objects. A later amendment may invalidate an inference or report without deleting its historical evidence. The [interoperability contract](INTEROPERABILITY_ARCHITECTURE.md) specifies what a connector may admit, preserve, reject or return.

See the [clinical core architecture decision register](ARCHITECTURE_DECISIONS.md) for the retained clinical base and its acceptance contracts.
