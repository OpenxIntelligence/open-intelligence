# Testing and evaluation

Engineering checks answer whether the software preserves its contracts. Clinical evaluation asks whether a specific function helps its intended user, with acceptable error and burden, compared with existing practice. Report the two separately. The [release record](RELEASE_ACCEPTANCE.md) owns version-specific evidence; the [AI evaluation plan](AI_EVALUATION_PLAN.md) owns model/extraction tasks and their adjudication. Current inputs are independently authored fictional records only.

## Engineering verification

The commands below run from the repository root with the applicable reviewed dependencies. The API workflow prepares/verifies hash-locked wheels and installs with `--no-deps --require-hashes --no-index`; the web workflow uses the committed lock, omits unreviewed optional packages and blocks install scripts. For database/recovery commands use a **disposable** PostgreSQL 16 `oi_api_test_*` instance with the exact URL, `PYTHONPATH`, `OI_API_ENVIRONMENT=synthetic`, `OI_API_TEST_DATABASE_URL` and `OI_API_RUN_DATABASE_TESTS=1` settings in [h1-api.yml](../../.github/workflows/h1-api.yml). Do not run migration tests against a retained demo or shared database.

## Evaluation before any clinical claim (OI-011 / OI-014)

1. The product owner writes an intended-use card: task, population, operator, decision supported, exclusions, human review and harm from a false statement, omission or delay. The evaluation lead freezes case-level splits, independent references, target error bounds, denominators and analysis before viewing outputs. Keep amendments, reports and relatives of the same fictional case in the same split; retain an unseen challenge set.
2. Compare the user's existing manual workflow and the simplest deterministic alternative against the candidate on the same cases. Include preparation, review, correction and time to locate the original. Two qualified independent reviewers, blinded to method when feasible, score independently under coded fictional case IDs, record disagreement and use a third adjudicator or documented consensus. A developer or model-as-judge score cannot establish clinical validity.
3. Separately count **critical clinical errors** (for example a wrong patient/specimen, flipped negation, invented dose/stage or an unsupported claim shown as reviewed), lesser semantic errors, ordinary software defects, refusals, missing outputs, latency and timeouts. Report counts/denominators, uncertainty, coverage, per-stratum failure and reviewer disagreement. Compute both per-case and per-claim rates so prolific output cannot dilute harm. Abstention can be appropriate or a clinically consequential omission; report which.
4. Freeze original labels, source anchors, versioned tool/model/prompt, hardware, cohort and rights. Stop on disclosure, wrong-subject write or unreviewed clinical promotion; quarantine and independently review any potentially serious error. A small synthetic set, a parser pass, upstream leaderboard or zero observed critical errors is not proof of safety. Re-evaluate after changes to data, prompts, model, adapters, intended use or grants. There is no independent clinical acceptance in this release record.
