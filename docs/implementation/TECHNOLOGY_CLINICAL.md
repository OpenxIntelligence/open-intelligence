# Clinical integration, terminology, documents, imaging and evidence: source review

Decision date: 2026-11-05. Scope: design and synthetic evaluation only. Retain the existing two scoped Python artifacts. No new library, clinical content, model, external service, API credential or production deployment is approved by this review. An offline validator, word-position parser, and DICOMweb viewer would address different gaps; none should expand platform permissions.

## How to read the code comparison

The revision link identifies the exact source commit screened (short label, full SHA in URL); the date is its observed commit day, an activity signal rather than proof of a supported release or a response to vulnerabilities. Each row links the license and a build/usage source inspected at that revision. For the two retained components the table also links the tag used by the application. A commit is a reproducible research reference, **not** an installation recommendation or an SBOM for any binary. Archives, packages, plugins, Docker images, language data and weights can introduce additional terms. Transitive SBOMs, vulnerability scans, performance and runtime validation are not claimed for candidate builds. No third-party data was downloaded.

Commercial modification/use and distribution are allowed by MIT/BSD/Apache for the covered code, subject to their actual terms: retain notices and license; BSD adds a non-endorsement condition; Apache requires preservation of applicable NOTICE material, marking modifications and compliance with its patent terms. MPL/LGPL/GPL/AGPL have different source/distribution conditions; AGPL additionally addresses remote interactions with modified covered software. The per-file terms and selected delivery mode must be reviewed; isolation alone is not clearance. A custom service or content agreement has no automatic SPDX software classification.

## C. Interoperability

Keep the application database authoritative. Validate an explicitly supported profile, then map references and terminology to canonical OI records only through existing tenant/source/review and clinical write authorization. Place staged imports, reports and profile-version evidence in existing provenance infrastructure. Disallow remote resource/terminology resolution, live endpoints, production FHIR writes, or broad bulk exports in synthetic evaluations.

Keep source code, dictionary files, mappings, definitions, licensed third-party synonyms and clinical conclusions distinct. Never ship an entire downloaded vocabulary or make an unrestricted proxy because its client code or the FHIR resource schema is permissive. The following records distinguish upstream permissions from OI deployment authorization: **no new resource or cache has been enabled.** When a grant or release cannot be confirmed, record “unknown” and require a scoped review; never substitute a moving alias for a proven data revision.

## E. Medical documents and OCR

Retain immutable source bytes, content digest and custody reference. Every derivative needs a new digest and input link; preserve original page number, coordinate unit and origin, media/crop box, rotation/DPI, text offsets and transformation to source. Distinguish absent text from parser failure and scanned-only input; fail closed on encryption, resource exhaustion and excessive embedded content. OCR confidence is not clinical certainty; human verification must resolve clinically meaningful units, signs, laterality and abbreviations. On a synthetic benchmark compare pypdf, PDFBox and pdfplumber for embedded text/locations; for scans, compare Tesseract and separately approved model pipelines on the same rasterized pages.
