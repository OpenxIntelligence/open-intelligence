# Open Intelligence — FHIR R4 laboratory intake: first implemented slice

**Status:** Synthetic-only, first-party, deterministic **preparation/preview**, not a clinical import, durable result, or clinical Patient World Model fact. No external FHIR connection, model execution, licensed terminology text or real patient data. Draft and unmerged until individually reviewed.

## The product correction

Open Intelligence is **modality-independent**, not PDF-first. One patient can contribute structured laboratory data, FHIR/HL7 payloads, DICOM studies, digitally signed reports, uploaded text/PDF, assays, genomics, patient-reported information, conversations and external research. Those forms require distinct parsers and rights/provenance rules. They do **not** require separate patient/source owners or a single universal document table. This increment targets **structured FHIR R4 data**, alongside (not replacing) existing H1 text/PDF and DICOM custody.

## Implemented and intentionally narrow

- `apps/api/src/oi_api/laboratory_fhir_r4.py`: standard-library-only parser for a **constrained FHIR R4 Bundle(collection)** with exactly one invented Patient and Specimen, 1–16 final laboratory Observations, and optionally one final DiagnosticReport linking exactly those Observations. Requires explicit LOINC source codes and UCUM codes; **does not resolve, redistribute or clinically interpret** terminology or convert units. It requires an explicit mapped external subject reference from the current owner, exact specimen links, full offset-bearing timestamps, an explicit numeric source value **or** data-absent reason, not both. Preserves exact incoming UTF-8 bytes and SHA-256, decimal precision, source-provided times, specimen, status and original reference IDs in an immutable, `persisted=False` candidate. Strict known-field subset; unsupported resources/statuses/fields are held, not partially inferred or silently discarded.
- `apps/api/src/oi_api/laboratory_fhir_routes.py`: new **authenticated, read-only preview** `POST /v1/patients/{patient_id}/cases/{case_id}/laboratory/fhir-r4/preview`. It reuses the existing H1 patient/case binding, independent `patient_read` + `source_import` permission checks, qualified source subject, canonical case lock and fresh final request credential/grant check. It serializes the exact preview before that final check. The route does not write any source, report, observation, event, patient or model row. The browser/client cannot assign an alternate external Patient mapping.
- Two test modules: deterministic parser refusals; and actual disposable PostgreSQL16/HTTP checks for scope, no-write source and domain-event counts, cross-actor and mismatched subject denial, revoked case, and mid-request source-import grant loss with no disclosure. The database-dependent tests need the hosted PostgreSQL environment and must **not** be claimed as locally passed.
- One independently invented JSON fixture under `examples/synthetic/` with a fictional patient, specimen, LOINC-coded observation and report; fixture metadata is not clinical/biomedical evidence.

The published parser accepts a strict engineering **subset of FHIR R4**, not arbitrary standards-conformant resources or every supported FHIR field; a rejection is a safety/coverage limit, **not** a claim that the source resource is invalid FHIR. Original external Patient identity mapping has **not been verified for production**: the provider-qualified synthetic binding exists for engineering. No external HTTP URLs are dereferenced; `fullUrl` is local `urn:uuid:` only. Source FHIR `Patient` contains no demographics or actual health information. No terminology catalog, LIS, external provider or data repository has been connected.

## Source lifecycle: what is deliberately not yet done

A successful preview **does not persist** its original bytes as a canonical source version, publish a Patient World Model observation, create a timeline event, import a signed lab result, mark a result negative or clinically verified, or attest consent. This is the first boundary of that workflow, not its completion. A downstream implementation **must reuse the existing H1 `PostgresSourceVersions` and case authority** to store exact original FHIR bytes and immutable version references, with a typed observation projection as a dependent view. It must not convert incoming FHIR to `OI-SYNTHETIC-REPORT/1` and discard original resource semantics. The existing source import accepts only fictional original text reports; it cannot be misrepresented as a FHIR source owner.

Next bounded vertical acceptance (same canonical owners): secure immutable FHIR payload import/versioning and byte-preserving exact retry; case/specimen/source/assay linkage; versioned read-only World Model and patient timeline projections; corrected/amended/withdrawn values with dependent-only invalidation; independently authorized raw-original download; authorization-before/after prepared responses; actual DB restart/dump/restore/case revocation; patient UI showing reported/unknown/no-result distinctly. Then implement other modalities using the same authority and provenance principles, not by forcing them into PDF/text.

## Required verification

1. Run deterministic parser tests and compile with no new third-party dependency, no network and independently fictional fixtures.
2. On the exact hosted head run actual PostgreSQL16/API tests including the HTTP no-write/revocation cases; all existing H1 migrations, authority gates and recovery must still pass, without relevant skips.
3. Run the H1 React/browser/rights workflow and existing synthetic source/reference tests to check no change to unrelated owners; retain exact SHA/artifact evidence and distinguish any transient Chrome bootstrap errors from product failures.
4. Independent security/clinical-terminology/interop review must approve any broader FHIR profile, recipient identity or eventual write behavior. No medical use, automatic action, real patient import or clinical release follows from these engineering tests.

**FHIR R4 reference:** [HL7 R4 Observation](https://hl7.org/fhir/R4/observation.html) and [HL7 R4 Bundle](https://hl7.org/fhir/R4/bundle.html). In particular, R4 distinguishes `value[x]` from `dataAbsentReason`, and DiagnosticReport references atomic Observations. These are external standards descriptions, **not** evidence of interoperability certification or a runtime dependency.
