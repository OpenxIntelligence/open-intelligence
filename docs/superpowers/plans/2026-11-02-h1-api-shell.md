# H1 API foundation — issue #112

## Objective and boundaries

Implement the accepted FastAPI/PostgreSQL 16 composition root in `apps/api`,
without replacing the existing SQLite prototype or introducing a second patient
registry. This is infrastructure for the connected investigation workflow, not
that workflow or approval for real-patient use.

Starting point: `533afd3ca6dd0c011e2e47397d3d5cae04e62512` on the synthetic-only
research safety branch (draft PR #137), whose parent is main
`24519839aa8ac1ea3aff88a956349ba72798a72a`. This contribution is stacked on that
safety correction; it does not merge it. Existing patient-port, clinical-spine,
source-correction, composer and review-receipt branches retain their ownership.

Authority: issue #112, parent #96, and the existing
[H1 decision register](https://docs.google.com/document/d/1YrORrdNxzT6MN-WuKVdk2vWVtVXVw9OSo0z5ARvMypg/edit).
Python 3.12, FastAPI, Pydantic 2, SQLAlchemy 2, Alembic and PostgreSQL 16 are the
accepted direction. Exact artifacts still need separate rights evidence. No
Next.js, vectors, acute alerts, patient acquisition or clinical endpoints.

## Work packages

1. Write failing tests for typed liveness/version contracts, fail-closed database
   readiness, sanitized configuration errors and the absence of patient routes.
2. Implement an application factory and bounded SQLAlchemy/pg8000 readiness
   adapter. Keep schema changes out of imports and application startup.
3. Add explicit Alembic migration commands and a version-only baseline. Verify
   real PostgreSQL 16 migration, downgrade, re-upgrade and process restart using
   a disposable synthetic database. No application-domain table is created.
4. Pin the exact resolved Python wheels with hashes. Inspect their licenses,
   embedded/native components and notices; create an artifact-specific inventory
   and fail-closed verification script. Container/OS tooling is a separate scope.
5. Add a local-only Compose stack with migration-before-serve and a pinned CI
   workflow checking the exact contribution head. Run existing regression tests.
6. Review the integrated diff independently, correct concrete findings, publish
   a focused draft contribution and record actual execution and remaining gaps.

## Acceptance and evidence ledger

- `/health` remains available during database failure.
- `/health/ready` returns 503 for missing/unreachable databases, non-16 servers,
  and missing/wrong schema; 200 only after the expected migration.
- `/v1` and `/v1/openapi.json` describe the synthetic shell honestly and expose
  no patient/clinical action endpoints or fabricated authentication.
- Secrets, DSNs and database exception details do not enter responses/logs.
- Migrations are explicit, reversible for this empty baseline and restart-safe.
- Locked Python artifact checks reject unexpected, changed or uncleared wheels.
- Local unit/HTTP execution and hosted PostgreSQL/Compose execution are recorded
  separately. Missing Docker in the session is not a Compose test pass.
- Existing prototype regression results and the exact tested commit are recorded.

Execution results, remaining requirements/component mappings and hosted-CI
evidence will be recorded in `apps/api/README.md` and the draft PR. Do not claim
MRT-01 patient workflow completion from this shell.
